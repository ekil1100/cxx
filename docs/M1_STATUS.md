# M1 实现进展与验证

## 结论

已开始 M1.2，交付 SharedLibrary/ObjectLibrary、生成文件与单输出 Custom Action，以及测试/显式前缀安装的最小闭环。公共 Build API 保持 C++17，Core/Runtime 使用 C++23。本机 macOS arm64 / Apple Clang 21 的 43 项 GoogleTest C++ 单元测试及 119 项 pytest 测试通过，其中 22 项覆盖库语义，11 项覆盖生成动作，17 项覆盖测试与安装。完整验证已覆盖链接来源修复；Linux 原生验证仍待执行。

M1 尚未完成。Linux 原生加载器执行及新测试的远端结果待验证；Windows、多输出 Custom Action、安装事务/卸载、并行调度及其他工作包保持待实现。本轮按用户要求与 M0 的 CI 验收并行推进，不将本机通过计作远端验收。

## 当前交付

| 能力 | 语义 |
|---|---|
| `Build::shared_library()` | Linux 输出 `.so`，macOS 输出 `.dylib` |
| `Build::object_library()` | 仅生成 `.objects`，没有独立归档或链接动作 |
| 对象消费 | executable/static/shared 可直接消费对象依赖，也可省略自身源码；对象库自身至少有一个源码 |
| 可见性 | 编译要求沿用 private/public/interface；链接输入单独计算 |
| 静态依赖 | 未解析的私有库依赖以 link-only 形式传播；消费者先于被依赖库排列 |
| 动态依赖 | 私有依赖停在动态库边界；运行时依赖仍进入构建图和输入摘要 |
| PIC | 所有库源码使用 `-fPIC`，以避免对象变体；静态库独占场景可能承担额外代码生成成本 |
| 运行时布局 | Linux SONAME 与 `$ORIGIN`；macOS `@rpath` 与 `@loader_path`；完整构建树可以整体搬移 |
| 增量 | 目标输入和运行时依赖内容参与摘要；空构建零 Compile/Archive/Link |

对象去重按实际消费动作处理。共享库只记录自身实际吸收的对象，私有运行时依赖保留独立的对象归属。每个目标先确定最终对象输入，再生成下游接口。每组裸对象保留自身尚待解析的库依赖，独立公开库要求单独保存。公开对象由共享库替代时，该提供者及其公开要求继续经过后续共享层传播；对象实际被吸收时，仅解除对应组的私有依赖。部分吸收、嵌套对象以及分开的私有与接口边遵循同一规则，保留下游链接顺序。可执行文件和共享库链接时，显式裸对象排在静态归档之前，即使归档包含同一对象也保留裸对象，以执行仅含构造器的注册代码。静态归档成员继续按需提取。独立库之间的进程级符号唯一性、whole-archive 以及显式符号导出控制留待后续。

## 生成文件与单输出动作

- `Build::custom_action(name)` 声明动作；`output(filename)` 返回带生产者身份的 `GeneratedFile`。句柄可复制，在所属 Build 生命周期内有效，跨 Build 使用会报错。
- 输出限制为 `.cxx/generated/<action>/<filename>` 下的单个文件；拒绝路径穿越、符号链接输出目录以及输出/元数据所有权冲突。
- `command(argv)` 显式调用已有宿主工具，不隐式运行 shell。输出路径必须作为独立参数出现，执行时替换为暂存文件路径；脚本应向收到的输出参数写入内容。
- `input(path)` 声明普通文件输入，`input(file)` 声明生成文件输入及其生产者依赖。工具文件、继承环境、命令和输入内容进入本地指纹；解释器加载的脚本和额外数据需要显式声明。
- `Target::source(file)` 添加生成源码与顺序依赖；`depends_on(file)` 为生成头建立前驱，include 目录仍由调用者声明。需要读取生成头的每个目标都应声明相应前驱。
- 默认动作每次执行；`.cacheable()` 表示调用者承诺声明输入闭包完整。没有沙箱或自动输入发现，缓存不适用于读取未声明文件、时钟或网络等不确定输入的工具。
- 全部声明先校验，再执行选定闭包；生成动作就绪后才进行消费者预处理扫描。默认 `build` 执行全部动作，指定 target 只执行所需生成前驱。纯动作项目支持默认 `build`，按动作名独立选择暂未提供。
- 命令失败、未产生普通文件或检测到执行中输入改变时，保留旧输出与旧 key；成功后经现有暂存发布机制更新。该保证不包括工具绕过传入路径直接修改旧文件，也不等同于沙箱或断电持久化。

边界保持为单输出、串行执行、已有宿主工具和显式依赖。多输出事务、项目内构建的工具目标、环境覆盖接口、跨平台 Host/Target 工具身份及自动生成头发现留待后续。

## 测试与安装

- `b.test(name, executable, args)` 注册同 Build 的可执行目标。`cxx test [filter] [-v]` 使用区分大小写的字面子串过滤，构建选定闭包后从项目根目录顺序运行。测试始终执行，首次失败即停止并传播退出码；无注册项/无匹配项报错。
- `b.install(target)` 声明可执行文件、静态库或共享库；对象库直接安装报错。`b.install_file(source, destination)` 声明完整的前缀相对文件名，source 可为普通路径或生成文件句柄。
- `cxx install --prefix <dir> [-v]` 要求显式前缀，相对路径以项目根目录为基准。程序放在 `bin/`，库放在 `lib/`；所需共享库及其私有传递依赖自动加入，静态库仅在显式声明时复制。
- 安装用程序和共享库单独链接到 `.cxx/install/bin`、`.cxx/install/lib`，复用普通对象文件；使用安装布局的相对运行时搜索路径，普通构建产物保持原状。完整安装树可以整体搬移并脱离工程运行。
- 测试和安装均为已有 Action 图中的终端动作，依赖缓存命中不会跳过副作用。安装每次检查并复制目的文件，修复删除/损坏，保留源执行权限。
- 安装前检查完整目的地集合，拒绝碰撞、路径穿越、符号链接路径和已知输入/构建产物重叠。Build Driver 的传递头文件、Runtime 自举输入和项目编译扫描发现的头文件均纳入保护，缓存命中也刷新扫描结果。启动器通过项目锁保护下的 `.cxx/driver/inputs` 私有文件传递路径和完整性状态，Runtime 入口保持 C++17 兼容。
- 依赖路径有损或汇编输入未跟踪时，扫描明确标记为不完整。普通构建继续执行；安装在首次目的地写入前拒绝。完整扫描通过后，复查全部目的地与输入集合，再逐文件暂存并原子替换。

保证范围：已有目的文件在该文件复制失败时保留；全部动作前置检查不等于多文件事务。后续文件失败可能留下部分更新的前缀；不删除无关文件，不提供卸载或安装清单，也不承诺跨工程同时安装到同一前缀的协调。路径校验使用 ASCII 大小写折叠；拒绝包含符号链接的前缀（macOS 的 `/tmp` 应改用实际目录 `/private/tmp`）。Windows 和 Linux 原生加载器验证仍待完成。

### 先前对象接口修复的定向验证

共享库原先先裁剪导出对象，再对本地输入去重；对象被私有共享依赖提供后，当前库既未实际吸收该对象，也未向下游传递它。最小反例在修复前稳定出现 `value()` 缺符号链接错误。现在按依赖顺序逐个完成本地去重、最终归属和接口计算，下游读取完成后的接口。公开对象路径中未被吸收的对象保留所需库依赖；显式导出的共享库已提供对象时，接口继续去重，避免下游静态库重复归档。

本轮在 macOS arm64 / Apple Clang 21 上执行 `.venv/bin/python scripts/build.py`，随后仅执行 `.venv/bin/python -m pytest tests/m1_libraries.py --cxx=build/cxx -q`：17 项测试、41 项子测试通过。新增回归覆盖直接公开对象、包装对象、分开的私有与接口路径、依赖声明顺序，以及私有/公开/移除内部共享依赖的 24 组组合；另覆盖对象库、静态库和共享库三种下游路径的库顺序、增量修改与空构建，以及公开共享所有者对下游静态库的去重。原有仅含构造器对象、按需归档和私有共享归属回归继续通过。库测试文件的 Ruff 检查与格式检查通过。以上为先前定向验证记录；修复后的完整验证结果见下文，Linux 原生验证仍待执行。

### 链接来源修复的定向验证

两个最小反例在修复前均失败：共享层转发后，公开对象的提供者丢失，应用出现 `value()` 缺符号；分开的私有与接口对象边使已被吸收对象的私有 `secret` 库出现在应用链接命令中。

`src/runtime.cpp` 使用按对象分组的链接要求替换平面的导出/假设吸收接口。实现保持三项不变量：

| 状态 | 保证 |
|---|---|
| 实际内容 | 本地产物只记录实际输入的裸对象；共享库的私有依赖和按需归档各自保留归属 |
| 公开要求 | 独立公开库继续传播；公开对象被替代时，提升实际共享提供者及其公开要求 |
| 对象私有依赖 | 依赖跟随对应对象组；实际吸收或共享提供者替代只解除该组要求，其他对象组保持完整 |

静态归档保留未解析依赖。可执行文件和共享库继续将显式裸对象排在静态归档之前。编译用法传播保持独立；仅因链接需要而提升的提供者保持链接专用。

本轮在 macOS arm64 / Apple Clang 21 上执行 `.venv/bin/python scripts/build.py`，随后执行 `.venv/bin/python -m pytest tests/m1_libraries.py --cxx=build/cxx --compiler=clang++ -q --tb=short`：22 项测试、55 项子测试通过。新增 5 项测试覆盖两个最小反例、分开边与公开边等价、反向声明、部分混合对象接口、多个对象共用私有库、独立公开依赖保留、嵌套包装、直接消费与三层共享转发，以及提供者的公开依赖。运行时断言检查仅含构造器的源文件与嵌套对象初始化均恰好执行一次；反向链接测试确认应用直接调用私有 `secret()` 失败。原有 24 组可见性/顺序组合、按需归档、私有共享归属、增量修改和空构建回归继续通过。库测试文件的 Ruff 检查、格式检查及修改文件的空白检查通过。

随后执行完整入口 `.venv/bin/python scripts/build.py --test`：43 项 GoogleTest 与 119 项 pytest 全部通过，生成 JUnit 报告。Linux 原生执行仍待验证。

## C++ 单元测试框架

已将 `tests/support_test.cpp` 的手写 check/rejects 迁移为 GoogleTest 的 6 个套件，目前包含 43 个独立用例。固定版本为 v1.18.0，提交 `063de7e9578f82b369302001269680b4b1553359`；许可证与源码摘要纳入 `third_party/manifest.json`。仅引入 GoogleTest，不引入 GoogleMock 或 gtest_main，生产启动器不链接测试框架。

根 `build.cpp` 直接编译 gtest-all.cc 并生成测试静态库，无需 CMake 或构建时下载。自定义 main 在 GoogleTest 初始化前处理进程测试的子入口，保留 1000 次并发启动回归。每个 fixture 独立清理临时目录，PATH 修改通过 RAII 恢复。

可通过 `./build/cxx test support` 构建并运行；也可直接使用 `./build/support_test --gtest_filter=...`、`--gtest_list_tests` 和 `--gtest_output=xml:...`。Python 端到端测试由 pytest 统一运行，保留原有 unittest.TestCase 断言及生命周期。

## Python 测试入口

pytest 9.1.1 固定在 `requirements-test.txt`，仅开发验证需要安装。`scripts/build.py --test` 先运行 GoogleTest，再以一次 pytest 调用运行全部 Python 测试，报告位于构建输出目录的 `pytest-results.xml`。CI 安装测试依赖并上传报告。

新增根目录 `conftest.py` 统一 `--cxx`、`--compiler` 与模块级准备。pytest 路径选项使用 `--cxx=PATH`、`--compiler=PATH`，防止路径值干扰测试发现；编译器路径保留符号链接及 `..` 语义。P02 的编译准备按需执行；只收集测试、只运行工具检查时无需构建 CXX 或可用编译器。移除各测试脚本独立的 argparse/unittest.main 入口，P04 的真实编译器探针继续独立运行。

可用 `task e2e -- -k noop`、`-m e2e`、`-m prototype`、`-m tooling` 筛选。暂不配置并行插件，避免共享 fixture 目录和真实编译器资源相互干扰。原有 99 个测试保留，新增 4 个入口/工具检查及 16 个库/安装回归测试，共 119 个。
